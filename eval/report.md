## 改进轨迹

### 2026-07-21：语料扩充（issue comments + 修复 ingest 窗口漂移）

改动：`ingest` 增加抓取 issue comments（之前只抓 body）；同时修了一个隐藏 bug——`fetch_closed_issues`
没有固定时间上界，仓库持续有新 issue 关闭，每次重跑会把最旧的 issue 挤出固定大小的窗口，导致
gold.jsonl 里标注过的 3893/3894/3896 从语料里消失。加了 `FETCH_CUTOFF` 常量冻结抓取窗口，
`max_issues` 从 50 提到 60（只为找回被挤掉的 3 条，非语料扩容决策）。

语料规模：111 → 234 chunks（60 个 issue 正文 + 44 个 issue 下的 102 条评论）。

题目：gold.jsonl 30 条题目本身没有改动，用于对照"纯粹语料变大"对已有基线的影响。

| 指标 | 旧基线 | 新基线 | 说明 |
|------|------|------|------|
| Recall@5 | 0.9 | 0.9 | 不变——27 个原本命中的问题，正确 chunk 排名即使被新增内容挤了名次，仍留在 top-5 内 |
| MRR@5 | 0.79 | 0.7789 | 轻微下降——新增的 123 个 chunk 成为新的排名竞争对手，只可能把原有正确答案的排名往后挤，不可能往前提，属语料扩容的预期副作用，不是回归 |
| Gold set 大小 | 30 | 30 | 未变 |
| 耗时 | 39秒 | 28秒 | 波动正常，未做归因 |

结论：证明"语料变大不会破坏现有检索能力"，同时留下一个可解释的信号（MRR 微降）作为
"候选池变大会稀释排名"的真实证据。下一步在扩充后的语料上标注难题批次（释义型 + 强干扰项型），
再看真实的 recall/MRR 变化。
### 2026-08-20：评测集 v2——为"看得见的改进"重建题目

#### 动机

dense-only 基线 Recall@5 已经是 0.9，天花板太近。更关键的是**旧题缺的不是难度，是区分度**：
30 条题里绝大多数在问题句里直接写了语料独有的稀有标识符（`logDetailCat`、`initLogPath`、
`callbackLogPath`、`addressList`、`openjdk:21-jdk-slim`、`unmappable character (0xC6)`）。
这类题 dense 能秒杀、BM25 也能秒杀，**混合检索的增量在这批题上天然为零**——
就算把 RRF 融合和重排做完，数字也不会动。

#### 改动一：修正 6 条过期标注（gold.jsonl）

2026-07-21 把 issue 评论并入语料后，有 6 条题的 `answer_points` 就过期了——它们写着
"应拒答，语料中没有找到明确答案"，但评论区里其实有维护者的明确回复：

| issue | 原标注 | 语料里实际有的（评论） |
|---|---|---|
| 3893 | 无答案 | 两个版本支持搭配使用，不要求版本必须一致 |
| 3894 | 无维护者回复 | 短期不考虑内置线程池 |
| 3900 | 无修复计划 | 建议升级 3.x 新版本，低版本排期中 |
| 3914 | 只有截图无结论 | 当前设计为 long，理论不会触达上限 |
| 3917 | 只有截图无结论 | 建议在业务逻辑内做幂等处理 |
| 3934 | 无维护者确认 | 终止为单任务维护，可以参考文档说明 |

只改 `answer_points`，`question` 与 `expected_sources` 一行未动，所以
**Recall@5 = 0.9 / MRR@5 = 0.7789 这组冻结基线仍然可比**。
（3896「请按 ISSUE 模板提供信息」、3902「需进一步提供复现步骤」、3908 无评论、3910「无法复现」
——这 4 条的拒答标注仍然成立。）

这类错误的危害不在检索指标（编号没错），而在 Week 3/4 的 groundedness / faithfulness：
参考答案本身是错的，模型答对反而会被判错。

#### 改动二：新增 v2 难题集（eval/gold_hard.jsonl，20 条）

v1 的 30 条**冻结保留**作回归哨兵——检索改完它应该稳在 0.9，掉了就是真回归。
v2 另开一个文件，按**检索机制**分五类出题，每条带 `tags` 以便按类别切分指标：

| 类别 | 条数 | 机制 | 预期 |
|---|---|---|---|
| 释义型 | 5 | 问题句与目标正文词面重合度≈0 | BM25 必挂，dense 该赢 |
| 标识符型 | 5 | 问题句携带罕见字面串（报错栈、CVE 号、配置项） | dense 会把长栈"平均"掉，BM25 该赢 |
| 干扰项型 | 4 | top-5 会被 2-3 条近似兄弟占满 | 主要压 MRR / Recall@1 |
| 多来源型 | 3 | `expected_sources` 有 2-3 个 | Recall 才有真实梯度 |
| 答案在评论 | 3 | 答案只在 `issue_comment` chunk 里 | chunk 更短、上下文更少，更难召回 |

设计前提做了机械验证（不是靠感觉）：

- 释义型 5 条：ASCII 标识符命中 0/0，中文 4-gram 与目标正文重合率 **0%** → BM25 拿不到任何信号
- 标识符型 5 条：ASCII 标识符命中率 **100%**（3/3、7/7、3/3、8/8、2/2）→ BM25 精准命中

用上了语料里现成的干扰项簇：`logDetailCat` 越权有 **3 份独立报告**（3983 / 3975 / 3936，
维护者回应互不相同）、SSRF 有 2 份（3935 / 3924）、"xxlJob调度丢失"有 2 份标题正文
几乎一样的（3947 无回复 / 3948 有维护者的三条建议）、PowerShell 编码有 2 份（3921 / 3930 被合并）。

#### 一个必须先说清的预期

**Recall@5 未必会掉很多。** 干扰项型题的近似兄弟会一起进 top-5，正确那条也在里面，
Recall@5 照样算命中——这类题真正压的是 **MRR 和 Recall@1**。
所以这批题的区分度主要体现在排名指标上，而不是命中率上。
这也正是下一步必须把 `run_eval.py` 从只报 @5 扩成同时报 **Recall@1 / @3 / @5 / @10 + MRR@10** 的原因：
重排器的全部价值就是把正确答案从第 3-5 名提到第 1 名，没有 @1 / @3 这两列，**重排做完了也看不出效果**。

预期区间：Recall@5 落在 0.7–0.85，MRR@5 落在 0.45–0.60。
若 Recall@5 仍 ≥ 0.9 且 MRR@5 ≥ 0.75，说明出题方向不对，优先加重干扰项型和长报错栈型。

#### 基线数字

先按**旧口径**（issue 级：召回目标 issue 的任意一段即算命中）跑了一版，结果是
Recall@5 = 0.9 / MRR@5 = 0.8417——**比 v1 还高**。复盘发现问题不在题目，在**评测口径太松**：

`expected_sources` 标的是 issue 编号，而一个 issue 会被切成多段。20 条题的平均"靶面"是
**7.2 段 / 全库 234 段**；更糟的是我专挑干扰项簇出题，而那几个簇恰好是全库最长的 issue
（安全报告写得细，被切成十几段）——`[3983, 3975, 3936]` 这一题的靶面是 **26 段，占全库 11%**，
随机抓 5 段都有四成几率"命中"。**靶子最大的几道，被我当成了最难的几道。**

同时暴露出一个此前没注意的现象：**top-5 个 chunk ≠ top-5 个 issue**。同一个长 issue 的多个段会
挤占多个名额，20 题的 top-5 平均只覆盖 **3.9 个**不同 issue，最少的只覆盖 2 个。长 issue 双重占便宜：
靶子大，还挤掉别人的位置。

于是把判定口径从 issue 级收紧到**引文级**：给每条题标一句 ≤40 字的答案原文
（新字段 `expected_evidence`），命中条件改为**「这一段属于期望 issue **且** 包含引文」**。
平均靶面从 7.2 段降到 **1.2 段**。

> 为什么标"引文"而不是直接标 chunk 编号：Week 2 还有一项 chunking 实验（对比不同
> chunk size / overlap）。标编号的话，一改切块参数所有编号重排、标注全部作废；标引文则只需
> 重新解析一次。这个改动顺手把原本没法做的 chunking 实验解锁了。引文控制在 40 字以内，
> 是为了在 overlap 变小后仍能完整落在某一段内。

| 指标 | v1 (30 条，冻结，issue 级) | v2 (20 条，难题，issue 级) | **v2 (20 条，难题，引文级)** |
|------|------|------|------|
| Recall@5 | 0.9 | 0.9 | **0.45** |
| MRR@5 | 0.7789 | 0.8417 | **0.2958** |
| 平均靶面 | — | 7.2 段 | **1.2 段** |
| 耗时 | 28 秒 | 353 秒(冷启动) | 90 秒 |

**这三列不能横向比高低**——前两列是 issue 级口径，第三列是引文级口径，衡量的不是同一件事。
v1 那列继续作为冻结回归哨兵（改检索后应稳在 0.9），提升轨迹从第三列开始记。

Recall@5 = 0.45 留出了 0.55 的空间，MRR@5 = 0.2958 更是几乎全是余量——
RRF 融合、重排、chunking 每一步的增益从现在起都能量出来。

#### 刻意留到 Week 3 的事

真·无答案题（`expected_sources: []`）**没有**放进 v2。原因是 `run_eval.py` 目前用
`next((i for i, sid in enumerate(list_source_ids) if sid in source_id), None)` 定位命中，
`expected_sources` 为空时永远返回 `None`，会被算成"检索失败"——放 4 条进去就白白把 Recall
拉低 0.2，把新基线搞脏。

已 grep 确认语料中完全不存在的话题，可安全用作拒答题：
Kafka / RabbitMQ / PostgreSQL / Prometheus / 灰度发布 / 单元测试。
留到 Week 3 做拒答护栏时单开 `eval/gold_refusal.jsonl`。

#### 失败模式：找对了文章，找错了段落

引文级口径下 20 条题命中 9 条。把两次结果并排看，**有 9 条题是从「issue 级命中第 1 名」
直接掉到「引文级未命中」的**——也就是说检索把正确的 issue 排到了第一位，但召回的是这个 issue 的
其它段落，不是含答案的那一段。

典型的几条，把问题句和证据段并排放就很清楚：

| 问题问的是 | 证据段实际写的是 |
|---|---|
| `NoSuchFileException` 出现在 `JobLogFileCleanThread` 这条链上，官方怎么答复 | "master分支已经优化推送，将随下个版本发布。" |
| `CVE-2025-7787` 针对 jdk8 的修复排期 | "建议升级3.x新版本，低版本排期中" |
| 监控首页统计曲线连续几天是空的 | "低版本异常情况下存在守护线程中断问题，建议升级。" |
| 两份 SSRF 报告维护者分别怎么回应 | "属于用户主动行为" / "存在accesstoken安全验证" |

问题里的关键词，在答案段里一个都没有。而命中的那几条恰好相反——问题句几乎复述了证据段
（3936 的问题写"认为这里已经存在权限校验逻辑"，证据段就是"存在 执行器 权限检验逻辑"）。

**归因**：用户描述的是「现象 / 报错」，答案往往是一句「泛泛的回复」，两者在向量空间里离得很远
（vocabulary mismatch）。**这不是加 BM25 能解决的**——"master分支已经优化推送"和
"NoSuchFileException"连一个共同词都没有，词面匹配同样无能为力；重排器也一样，它算的还是
query 与 chunk 的相关度。

一个已确认的相关事实：`src/index/main.py:103-106` 只把 `chunk["text"]` 送去嵌入，
`title` 只存进 payload、**从未进入向量**。所以"master分支已经优化推送"这一段的向量里
没有任何关于它属于哪个 issue 的信息——它和 3890 下面那条一字不差的回复在向量空间里几乎是同一个点。

> 方法论备注：曾试图用「问题↔证据段」与「问题↔标题」的字面重合度来预判"拼上标题能不能救"，
> 但这是词面指标（本质是 BM25 视角），而命中的 3968 / 3903 / 3894 字面重合度同样是 0%——
> **这把尺子量不了 dense 检索**。结论：不靠推断，直接做 A/B 实验。

#### 实验：嵌入内容加不加标题 —— 假设成立

改动：`src/index/main.py` 新增 `EMBED_WITH_TITLE` 开关和 `build_embed_text()`，
把送进嵌入模型的文本从 `text` 改成 `title + "\n" + text`。**payload 里存的仍是原始 text**，
所以检索结果的展示和评测比对逻辑完全不受影响。重建索引后重跑 v2（引文级口径，题目一字未改）：

| 组 | 嵌入内容 | Recall@5 | MRR@5 |
|---|---|---|---|
| 基线 | `text` | 0.45 | 0.2958 |
| **实验** | **`title + "\n" + text`** | **0.75** | **0.4683** |
| 差值 | | **+0.30** | **+0.1725** |

具体变化，以 3941 那条评论段为例：

```
改动前送进模型： "master分支已经优化推送，将随下个版本发布。"
改动后送进模型： "Caused by: java.nio.file.NoSuchFileException: /logs/service-user/...
                 master分支已经优化推送，将随下个版本发布。"
```

改动前这一段的向量里没有任何"我属于哪个 issue"的信息，和 3890 下面那条一字不差的回复
几乎是同一个点；改动后它带上了自己所属 issue 的标识，问"NoSuchFileException 官方怎么答复的"
才能搭得上。

**结论**：naive chunking 把段落切成孤立片段，短评论段因此丢失全部上下文。
两行代码的改动带来 +0.30 Recall / +0.17 MRR，**幅度大于混合检索和重排通常能给的增量**——
先修 chunk 的上下文，再谈换检索算法。

**诚实的保留意见**：v2 里有 5 条"标识符型"题刻意使用了语料中的罕见字面串（报错栈、CVE 号），
而其中若干串恰好就是 issue 标题本身（如 3941 的标题就是那条异常、3922 的标题是"偶现的Premature EOF"）。
**这批题的构造方式对"加标题"这个改动是有利的**，实测增益可能被高估。
不过这并不算脱离实际——真实用户确实会直接粘贴报错，而 issue 标题确实常常就是报错本身。
待语料扩容、题目来源更分散后需要复测这个数字。

#### 仍待做

  而 v1 没有该字段会 `KeyError`。v1 **不应该**补引文——它要留在 issue 级口径上才能继续和
